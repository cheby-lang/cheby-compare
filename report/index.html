Cheby: whole process at bench size 1.34 s; estimated compile 9.6 ms (median run at size 0); cheby check 8.0 ms.

  • Cheby runs ≈ 1.33 s, 17th of 20 and 1.34× Rust. That puts it next to the languages that free node by node: Rust (991 ms), C++ (1.12 s) and Odin (1.26 s) are just ahead, and Swift, also reference counted (ARC), is behind at 1.66 s. Most tracing collectors lead: Java 255 ms, Go 612 ms, OCaml 703 ms (Cheby 1.89×), Gleam 747 ms (1.77×) and Erlang 792 ms (1.67×). Elixir, at 989 ms, is level with Rust. Koka, the closest model to Cheby (Perceus over mimalloc), is the one reference-counted language far ahead, at 396 ms (Cheby 3.35×).
  • Peak RSS is 52.6 MB, against 17.9 MB for Rust and 254 MB to 413 MB for BEAM and JVM. 18.9 MB of Cheby's is the floor every cheby run process has, since it carries the compiler and the JIT: that is what hello_world peaks at. Without it Cheby would be at about 34 MB, still almost twice Rust and C++ (17.7 MB). Go (37.7 MB) and OCaml (46.6 MB), which use tracing collectors, peak below Cheby's total.
  • The work matches the SPEC: one heap object per node, freed by its count (D-005). The runtime's allocation counter (CHEBY_RT_STATS=1) shows one allocation per node at the test size. The SPEC requires one allocation and one free per node in every language, so those are not a cost of reference counting. What reference counting adds is small here: check borrows its tree, so the walk touches no counts, and one drop after check frees the whole tree, one decrement and one free per node (the program's MIR). Only that part is language design.
  • Most of the time goes to the runtime's own allocation and free path, not to mimalloc. A profile at depth 19 puts most samples in alloc_from, init_object, drain and shape_of in crates/cheby_runtime/src/alloc.rs, and only a small share in mimalloc's functions (D-890). Allocating does a budget check, a per-fiber block-cache lookup through thread-local storage and per-domain accounting. Freeing looks up each object's layout and walks a worklist. That is current implementation, which M3 and later may change. Koka, for comparison, frees each node inline while check walks it (see Koka's impl.toml).
  • The run time is an estimate, but a good one here. It is the bench run minus a size-0 run (≈ 9.6 ms), under 1% of the total, and the ten runs span only 1.31 s to 1.34 s.
  • Outside Cheby, the allocator likely explains much of the order among the malloc/free languages. Zig's nodes come from std.heap.smp_allocator and it runs in 504 ms, while Rust (991 ms) and C++ (1.12 s) use the macOS system malloc (see Zig's impl.toml). No run swapped the allocator to confirm it. Koka's 396 ms comes from its bundled mimalloc together with freeing each node inline as check walks it (Koka's impl.toml).

  • Cheby runs ≈ 44.0 s, 19th of 20 and 85.6× Rust. Only Python (51.4 s) is slower. The languages that rebuild immutable records in a list every step are its real peers, and Cheby trails all of them: Erlang 17.2 s (Cheby 2.56×), Elixir 23.8 s (1.85×), Gleam 26.2 s (1.68×) and Koka 2.78 s (15.8×). OCaml, with mutable float fields, runs 906 ms.
  • The language rules out the in-place version. Cheby has no mutation and no array type (D-017, D-039), so each step builds new Body records and a new list, as the SPEC expects. Koka's 2.78 s shows how fast immutable records can run under Perceus reuse (D-005). Its list is a cons list walked by direct recursion, the shape a later bullet finds several times faster in Cheby too.
  • The time goes to lists, allocation and reference counting, not to float arithmetic. A profile at a smaller step count puts most samples in the runtime's allocation and count functions and in its List kernels, with only a small share in compiled code. List is an RRB vector, not a linked list (D-039). Each [first, ..rest] pattern costs three runtime calls (ListLength, ListGet, ListSliceOwned in crates/cheby_mir/src/ir.rs). list::fold calls its closure through the uniform convention for unknown callees (D-453) and threads a fresh tuple accumulator. Each step also pushes and prepends to lists and maps over one.
  • Records read out of a List are often still shared, so their update cannot reuse them in place. cheby run --reuse-report shows that Body { ..a, ... } may reuse a when it is unique, but ListGet dups the element it reads, and the runtime counters show many of those reuses missing at run time. The same step written over a hand-made cons type, the shape Koka and the BEAM programs use, reused every record in place and ran several times faster in a scratch test at a smaller size. That gap is current implementation, not language design.
  • Floats are mostly not boxed here. A record keeps its Float fields raw (D-562, docs/plan/architecture.md), so reading and building bodies moves no boxed floats. The exception is float::sqrt, once per pair: a native external returns through a Cheby-ABI wrapper as a uniform word (D-455, D-453), so its result is a boxed Float. It is a small share of the profile.
  • Cheby's row is an estimate, from 3 timings. It is the bench run minus a ≈ 11 ms size-0 run, which is negligible here, and runs over 5 s get only 3 timings. Peak RSS is 21.4 MB, against 1.8 MB for Rust, and 18.9 MB of it is the floor of any cheby run process (hello_world).

  • Cheby runs ≈ 52.6 s, 19th of 20 and 65.5× Rust. Only Python (77.4 s, one timing) is slower, and Ruby (50.4 s) is just ahead (Cheby 1.04×). The list-walking languages are the fair comparison, and all are ahead: Erlang 8.58 s (Cheby 6.13×), Elixir 9.51 s (5.53×), Gleam 18.1 s (2.90×) and Koka 5.96 s (8.82×).
  • No arrays is language design, and it shapes the program. Cheby has no array type (D-039), so the vectors are List<Float> walked front to back, as in the BEAM languages and Koka. A Float inside a List is a boxed heap object (D-521), so every element read touches a separate object and updates its count.
  • float::from_int allocates on every matrix entry. It is a native external, and a native external is called through a Cheby-ABI wrapper that returns one uniform word (D-455, D-453), so its Float result is boxed, then unboxed and freed by the caller. The runtime counters show one allocation per inner step. In a scratch test at a smaller n, carrying the indices as Float, with no conversion in the inner loop, cut the run time by more than half. That cost is current implementation.
  • Each [xj, ..tail] step is three runtime calls. A list pattern lowers to ListLength, ListGet and ListSliceOwned (crates/cheby_mir/src/ir.rs), none of them inlined, and the first slice of every row copies the root of the shared input list. A profile puts the largest share of samples in these list kernels, then in allocating and freeing the boxed floats, and the smallest in compiled code. In the same scratch test, a hand-made cons type with raw Float fields also saved about half, and the two changes together removed most of the run time. So both costs are current implementation, not the arithmetic.
  • The program is already tuned around the boxing. A(i, j) is written out in both inner loops instead of being a helper, because a Float returned from a function is boxed (D-453). The Cheby impl.toml records the measurement behind that choice.
  • Boxed float returns are not unique to Cheby. OCaml marks its entry helper [@inline], since ocamlopt without flambda boxes a returned float, and Erlang and Elixir ask their compilers to inline a/2 (their impl.toml files).
  • Cheby's row is an estimate. It is the bench run minus a ≈ 12 ms size-0 run, which is negligible here, and runs over 5 s get only 3 timings. Peak RSS is 21.4 MB, against 1.9 MB for Rust, and 18.9 MB of it is the floor of any cheby run process (hello_world).

Cheby: whole process at bench size 2.13 s; estimated compile 10 ms (median run at size 0); cheby check 8.6 ms.

  • Cheby runs ≈ 2.12 s, 15th of 20 and 2.97× Rust. This is its best CPU rank, and its second-best CPU ratio to Rust after binary_trees (1.34×). Every AOT, JVM, CLR and JS runtime is ahead of it: Cheby takes 2.20× as long as OCaml (963 ms), 2.21× as long as Clojure (962 ms) and 2.75× as long as Koka (772 ms). It is ahead of the BEAM languages, which take 3.87× (Erlang, 8.21 s) to 4.06× (Gleam, 8.61 s) as long, and of Ruby and Python.
  • The inner loop allocates nothing. escape_time is a top-level function that calls itself in tail position, and a Cheby-ABI function keeps its Float parameters unboxed (D-453). The one allocation per point is the boxed result of float::from_int, a native external that returns through a uniform-word wrapper (D-455). The runtime counters show one allocation per point, and a profile puts only a small share of samples in allocating and freeing.
  • Every iteration is still a full function call. The disassembly of the JIT code shows each step run the whole prologue and epilogue: it saves callee-saved registers, signs the return address, spills its four Float parameters to the stack and checks the stack limit (D-028, D-453). Then it adds 1 to steps with an overflow check (D-025) and jumps back through the function's indirection slot as a Cranelift return_call. On native every tail call, self calls included, goes through the slot so that REPL redefinitions stay visible (D-015, D-043). The planned JS target (M4) will compile self recursion to loops. Each step also loads the constant max_iterations from its slot, with a dup and a drop, and the > compare takes three fcmp instructions. The float math is only a handful of the instructions in each step. The call overhead and the constant load are current implementation.
  • The program shape works around the boxing rules. The loops are top-level functions because a local function takes and returns uniform words (D-453), so every Float passing through it is boxed. The SPEC and Cheby's impl.toml record a local-loop version as several times slower. cr is computed inline and the totals are accumulator arguments, so no Float comes back from a call that is not a tail call, apart from float::from_int. That is why walk takes eight parameters, which, with loops written as recursion, accounts for much of Cheby's 66 lines against Rust's 41.
  • Cheby's row is an estimate, with little noise. It is the bench run minus a ≈ 10 ms size-0 run, with ten timings from 2.09 s to 2.16 s. Peak RSS is 20.0 MB, against 1.8 MB for Rust, and 18.9 MB of it is the floor of any cheby run process (hello_world).
  • Outside Cheby, twelve runtimes finish within 1.10× of the fastest. Swift, Odin, Zig, C++, Nim, Rust, Java, Go, TypeScript, C#, Scala and Koka all land between 705 ms and 772 ms. The loop is simple enough that the JVM, V8 and the CLR match the AOT compilers.

  • Cheby is fifth of the 19 comparable languages, in the lightweight-task band. Its estimated run time is ≈ 88 ms [87 ms–89 ms], and the whole process takes 99 ms. Go (16 ms, so Cheby is 5.39× slower), Swift (59 ms), TypeScript (62 ms) and C# (72 ms) are ahead. So are the rust-tokio (29 ms) and OCaml Eio (62 ms) variants. Java's virtual threads come right behind at 96 ms. Erlang takes 157 ms (1.78× Cheby), Gleam 197 ms and Elixir 342 ms. Rust's OS threads take 805 ms, 9.13× Cheby.
  • Each task does only ten generator steps, so the rows measure spawn and join. A Cheby spawn allocates the closure and a Fiber handle with its join cell, and marks the closure shared (D-705). It also takes a stack slot (8 MiB of address space, D-125, with free slots reused warm, D-677), builds a control block, and records the fiber in its scope under the scope's lock (crates/cheby_runtime/src/fiber_ops/spawn.rs). The new fiber takes the runnext slot. The fiber it displaces goes to the worker's deque, and an idle worker is woken through a condition variable (schedule and notify_parked in crates/cheby_runtime/src/sched/mod.rs). Each fiber takes the scope's lock again when it ends. The locking, the condition-variable wake-ups and the separate handle and join-cell allocations are the current implementation. Registering each fiber with its scope (structured concurrency, D-040) and giving each fiber its own stack (D-125) are design choices.
  • Waking workers and sharing the scope's lock show up in the profile. In a profile at a larger n, the spawn path is the largest item. Time also goes to the scope lock's slow path, where the spawner and the ending fibers meet, and to condition-variable waits and signals. The whole run spent 53 ms in the kernel, against 9.4 ms for Go.
  • The program's [fiber, ..fibers] is not a cheap cons, which is the current implementation. List is an RRB-tree vector, not a linked list (D-039, language design). The compiler lowers [x, ..xs] to a one-element list concatenated with xs (crates/cheby_mir/src/lower/list.rs), which allocates new tree nodes for every task. CHEBY_RT_STATS=1 counts about four more allocations per task than with list::prepend(fibers, x) or [..fibers, x], which update the list in place. A scratch copy that used [..fibers, x] ran clearly faster at a larger n. The program keeps the cons form, the idiom of the other functional rows. The compiler could lower it to the in-place prepend kernel.
  • With one worker thread, the stack pool hits a cliff, but this run avoids it. A stack class keeps at most 64 warm free slots (FREE_KEEP in crates/cheby_runtime/src/fiber/stack.rs), and a batch holds up to 1,000 live fibers. With CHEBY_THREADS=1, most slots are released whole and fault in again, which makes the run several times slower. With the default eight workers almost every slot is reused warm. Cheby's bench/runtime/README.md documents this.

Run-to-run spread was small: the whole process took 97 ms to 100 ms over ten runs. The implementation's notes record that it slows down far more than Go or rust-tokio when the CPU is oversubscribed. Koka's row (14 ms) is not comparable. Koka's standard std/async has no dynamic spawn (interleaved takes a fixed list of strands and returns no handle), so its program carries its own single-threaded cooperative scheduler, an effect handler with a queue. The row measures that scheduler, not a runtime's task primitive.

Swift takes 98 ms (4.95× Cheby's estimate), Java 207 ms (10.5×), the BEAM rows 238 ms to 272 ms (12.0× to 13.8×), Rust 538 ms (27.2×) and OCaml's systhreads 4.57 s (231×).
  • Capacity-0 channels let the pipeline run on several cores. Each handoff works as in ping_pong: the value goes straight into the parked receiver's wait node, and the receiver takes the runnext slot (crates/cheby_runtime/src/fiber_ops/channel.rs). With 801 stages, idle workers steal runnable stages, so different parts of the pipeline run at the same time. The whole run used 140 ms of user CPU in 31 ms of wall time, and Go shows the same pattern (183 ms). In a scratch run at a larger n, CHEBY_THREADS=1 was several times slower than the default eight workers. The BEAM rows follow the SPEC's pull protocol. It keeps one message in flight in the whole pipeline, so their stages cannot overlap.
  • The per-message costs from ping_pong apply here too, and they come from the current implementation. Each receive allocates an Ok(value) cell, since channel::receive returns a Result (D-054). Each send grows a heap worklist to mark a plain integer shared (D-705, crates/cheby_runtime/src/rc.rs). In a profile at a larger n, the stack switch comes first, then the channel kernels and these allocations.
  • Shutdown is cheap because the stages are detached. The program starts every stage with fiber::spawn_detached and returns from main, and the runtime kills the remaining fibers at exit (D-073). The tail's receiver is dropped when primes returns, so the last filters can end on their own. Nothing waits for the pipeline to drain.

Each of the 802 fibers has its own stack slot (8 MiB of address space, D-125), with its control block at the top (D-677), and it touches at least one 16 KiB page of that slot on Apple silicon. In scratch runs, peak memory grew by about that much for each extra fiber. The BEAM rows peak at 74.5 MB to 76.6 MB.
  • Some rows do slightly different work. Cheby's run time is an estimate: its bench run minus its 11 ms size-0 run, which includes eager JIT of the whole program. Rust-tokio, Python, Nim and Ruby use capacity-1 channels, so their stages can run one number ahead and do a few percent more filter work. Koka's 53.4 s row is not comparable: its std/async has no dynamic spawn, so each handoff costs O(pipeline depth).
  • Blocking condition variables slow the C++ row. C++ takes 1.99 s, 3.71× Rust, and spent 11.8 s of CPU in the kernel. Its implementation's notes trace this to libc++ on macOS, whose condition variable sleeps in the kernel at once. Rust's zero-capacity channel spins briefly before it parks.
