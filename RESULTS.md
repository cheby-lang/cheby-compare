  612 ms, OCaml 703 ms (Cheby 1.89×), Gleam 747 ms (1.77×) and Erlang 792 ms (1.67×). Elixir, at
  989 ms, is level with Rust. Koka, the closest model to Cheby (Perceus over mimalloc), is the one
  reference-counted language far ahead, at 396 ms (Cheby 3.35×).
- **Peak RSS is 52.6 MB, against 17.9 MB for Rust and 254 MB to 413 MB for BEAM and JVM.** 18.9 MB
  of Cheby's is the floor every `cheby run` process has, since it carries the compiler and the JIT:
  that is what `hello_world` peaks at. Without it Cheby would be at about 34 MB, still almost twice
  Rust and C++ (17.7 MB). Go (37.7 MB) and OCaml (46.6 MB), which use tracing collectors, peak
  below Cheby's total.
- **The work matches the SPEC: one heap object per node, freed by its count (D-005).** The runtime's
  allocation counter (`CHEBY_RT_STATS=1`) shows one allocation per node at the test size. The SPEC
  requires one allocation and one free per node in every language, so those are not a cost of
  reference counting. What reference counting adds is small here: `check` borrows its tree, so the
  walk touches no counts, and one `drop` after `check` frees the whole tree, one decrement and one
  free per node (the program's MIR). Only that part is language design.
- **Most of the time goes to the runtime's own allocation and free path, not to mimalloc.** A
  profile at depth 19 puts most samples in `alloc_from`, `init_object`, `drain` and `shape_of` in
  `crates/cheby_runtime/src/alloc.rs`, and only a small share in mimalloc's functions (D-890).
  Allocating does a budget check, a per-fiber block-cache lookup through thread-local storage and
  per-domain accounting. Freeing looks up each object's layout and walks a worklist. That is current
  implementation, which M3 and later may change. Koka, for comparison, frees each node inline while
  `check` walks it (see Koka's `impl.toml`).
- **The run time is an estimate, but a good one here.** It is the bench run minus a size-0 run
  (≈ 9.6 ms), under 1% of the total, and the ten runs span only 1.31 s to 1.34 s.
- **Outside Cheby, the allocator likely explains much of the order among the malloc/free
  languages.** Zig's nodes come from `std.heap.smp_allocator` and it runs in 504 ms, while Rust
  (991 ms) and C++ (1.12 s) use the macOS system `malloc` (see Zig's `impl.toml`). No run swapped
  the allocator to confirm it. Koka's 396 ms comes from its bundled mimalloc together with freeing
  each node inline as `check` walks it (Koka's `impl.toml`).

### Notes

- **Cheby runs ≈ 44.0 s, 19th of 20 and 85.6× Rust.** Only Python (51.4 s) is slower. The languages
  that rebuild immutable records in a list every step are its real peers, and Cheby trails all of
  them: Erlang 17.2 s (Cheby 2.56×), Elixir 23.8 s (1.85×), Gleam 26.2 s (1.68×) and Koka 2.78 s
  (15.8×). OCaml, with mutable float fields, runs 906 ms.
- **The language rules out the in-place version.** Cheby has no mutation and no array type (D-017,
  D-039), so each step builds new `Body` records and a new list, as the SPEC expects. Koka's 2.78 s
  shows how fast immutable records can run under Perceus reuse (D-005). Its list is a cons list
  walked by direct recursion, the shape a later bullet finds several times faster in Cheby too.
- **The time goes to lists, allocation and reference counting, not to float arithmetic.** A profile
  at a smaller step count puts most samples in the runtime's allocation and count functions and in
  its `List` kernels, with only a small share in compiled code. `List` is an RRB vector, not a
  linked list (D-039). Each `[first, ..rest]` pattern costs three runtime calls (`ListLength`,
  `ListGet`, `ListSliceOwned` in `crates/cheby_mir/src/ir.rs`). `list::fold` calls its closure
  through the uniform convention for unknown callees (D-453) and threads a fresh tuple accumulator.
  Each step also pushes and prepends to lists and maps over one.
- **Records read out of a `List` are often still shared, so their update cannot reuse them in
  place.** `cheby run --reuse-report` shows that `Body { ..a, ... }` may reuse `a` when it is
  unique, but `ListGet` dups the element it reads, and the runtime counters show many of those
  reuses missing at run time. The same step written over a hand-made cons type, the shape Koka and
  the BEAM programs use, reused every record in place and ran several times faster in a scratch test
  at a smaller size. That gap is current implementation, not language design.
- **Floats are mostly not boxed here.** A record keeps its `Float` fields raw (D-562,
  `docs/plan/architecture.md`), so reading and building bodies moves no boxed floats. The exception
  is `float::sqrt`, once per pair: a native external returns through a Cheby-ABI wrapper as a
  uniform word (D-455, D-453), so its result is a boxed `Float`. It is a small share of the profile.
- **Cheby's row is an estimate, from 3 timings.** It is the bench run minus a ≈ 11 ms size-0 run,
  which is negligible here, and runs over 5 s get only 3 timings. Peak RSS is 21.4 MB, against
  1.8 MB for Rust, and 18.9 MB of it is the floor of any `cheby run` process (`hello_world`).

### Notes

- **Cheby runs ≈ 52.6 s, 19th of 20 and 65.5× Rust.** Only Python (77.4 s, one timing) is slower,
  and Ruby (50.4 s) is just ahead (Cheby 1.04×). The list-walking languages are the fair comparison, and all
  are ahead: Erlang 8.58 s (Cheby 6.13×), Elixir 9.51 s (5.53×), Gleam 18.1 s (2.90×) and Koka
  5.96 s (8.82×).
- **No arrays is language design, and it shapes the program.** Cheby has no array type (D-039), so
  the vectors are `List<Float>` walked front to back, as in the BEAM languages and Koka. A `Float`
  inside a `List` is a boxed heap object (D-521), so every element read touches a separate object
  and updates its count.
- **`float::from_int` allocates on every matrix entry.** It is a native external, and a native
  external is called through a Cheby-ABI wrapper that returns one uniform word (D-455, D-453), so
  its `Float` result is boxed, then unboxed and freed by the caller. The runtime counters show one
  allocation per inner step. In a scratch test at a smaller `n`, carrying the indices as `Float`,
  with no conversion in the inner loop, cut the run time by more than half. That cost is current
  implementation.
- **Each `[xj, ..tail]` step is three runtime calls.** A list pattern lowers to `ListLength`,
  `ListGet` and `ListSliceOwned` (`crates/cheby_mir/src/ir.rs`), none of them inlined, and the first
  slice of every row copies the root of the shared input list. A profile puts the largest share of
  samples in these list kernels, then in allocating and freeing the boxed floats, and the smallest
  in compiled code. In the same scratch test, a hand-made cons type with raw `Float` fields also
  saved about half, and the two changes together removed most of the run time. So both costs are
  current implementation, not the arithmetic.

  function, and the syntax pass took most of the run. Decoding and writing took the rest.
- **The decoders and the writer add more allocation.** `decode::list` formats an index into the

  record's `use` chain builds fresh decoder closures. On output, `json::to_string` keeps an
  explicit stack of steps so that deep documents cannot overflow the stack (D-094, D-326). Its

  escape.

  says. Python's and Ruby's parsers are written in C. Rust, C++, Java, Scala, Clojure, OCaml and

- **Two library effects stand out in the other rows.** Ruby's C-extension `json` (1.52 s) beats
  C++ with nlohmann/json (1.90 s). Gleam parses with the same OTP `json` module as Erlang, but
  decodes into typed records through `gleam/dynamic/decode`, and takes 2.97× Erlang's time.

- **Cheby ties Erlang and Elixir, 47× slower than Rust.** Its estimated run is 31.3 s, 18th of 20,

  their min-max ranges overlap Cheby's. Clojure (27.9 s) and Gleam (24.5 s) are faster, Koka

  and Elixir (about 320 MB), Gleam (247 MB) and Clojure (2.1 GB), but over Rust's 11.3 MB.
- **Without mutation there is no linked list, by design.** Cheby has no mutable state (D-017), so
  neither shape B's doubly linked list nor an in-place `LinkedHashMap` can be written. Its
  shape A, `std::ordered_map`, is shape C inside: a `Map<K, (Int, V)>` plus a
  `SortedMap<Int, K>` from insertion number to key (`std/ordered_map.cheby`, D-336). So the rows
  to compare with are the other shape C rows (Erlang, Elixir, Clojure, Gleam, Koka), and Cheby
  lands among them.
- **A hit costs five hash operations and two tree updates.** `ordered_map` has no move-to-end, so
  a hit is `get`, `remove` and `insert` (D-340). `remove` and `insert` each start with their own
  `map::get`. A hit is therefore three hash lookups, a hash remove, a hash insert, and a
  `sorted_map::remove` and `insert`. A miss in a full cache also pays for `first` and the evict:
  four lookups, a hash remove, a hash insert and three tree operations in all. Every `map::get`
  that finds its key also allocates a `Some`. A move-to-end or pop-first operation in the standard
  library would save part of this work.
- **The cache is updated in place, but each step walks a tree.** Only the loop holds the cache,
  so Perceus reuse writes rebuilt tree nodes over the old ones and the hash trie changes in place.
  A test-size run with `CHEBY_RT_STATS=1` reported no copied map update. What is left is the work
  itself. Without mutation, an O(log n) weight-balanced tree (`std/sorted_map.cheby`) stands where
  shape B has an O(1) linked list. That tree compares keys through the `Compare` dictionary
  (D-046), because generic code is not yet specialized (D-021); specialization is planned for M6
  (D-251). In a profile at a tenth of the bench operations, JIT-compiled Cheby took about three
  fifths of the samples, the runtime's hash kernels about a fifth, and its allocation and
  reference counting about a seventh. Persistence alone does not explain the gap: Koka's
  persistent tree is 2.23× faster here.
- **The runtime adds one avoidable cost per update.** `Path::walk` in
  `crates/cheby_runtime/src/hamt/ops.rs` allocates two `Vec`s for every `map::insert` and
  `map::remove`, to record the path it walks. This belongs to the current implementation.
- **The rows use three shapes.** Java, Scala, Ruby, Python and Cheby use an ordered map (A). Rust,
  C++, Go, C#, TypeScript, Swift, Zig, Odin, Nim and OCaml use a hash map plus a linked list (B).
  The BEAM languages, Clojure and Koka use two persistent maps (C), and Koka writes its own tree.
  Cheby's estimate makes no difference here: the size-0 run takes 15 ms against a 31.3 s whole
  run.
- **Ruby beats two shape B rows with a plain `Hash`.** Its delete-and-reinsert hit (2.06 s) is
  faster than OCaml (2.52 s) and TypeScript (2.65 s), which both keep a hash map plus a linked list.

  fiber takes the scope's lock again when it ends. The locking, the condition-variable wake-ups
  and the separate handle and join-cell allocations are the current implementation. Registering
  each fiber with its scope (structured concurrency, D-040) and giving each fiber its own stack
  (D-125) are design choices.
- **Waking workers and sharing the scope's lock show up in the profile.** In a profile at a larger
  `n`, the spawn path is the largest item. Time also goes to the scope lock's slow path, where the
  spawner and the ending fibers meet, and to condition-variable waits and signals. The whole run
  spent 53 ms in the kernel, against 9.4 ms for Go.
- **The program's `[fiber, ..fibers]` is not a cheap cons, which is the current implementation.**
  `List` is an RRB-tree vector, not a linked list (D-039, language design). The compiler lowers
  `[x, ..xs]` to a one-element list concatenated with `xs`
  (`crates/cheby_mir/src/lower/list.rs`), which allocates new tree nodes for every task.
  `CHEBY_RT_STATS=1` counts about four more allocations per task than with
  `list::prepend(fibers, x)` or `[..fibers, x]`, which update the list in place. A scratch copy
  that used `[..fibers, x]` ran clearly faster at a larger `n`. The program keeps the cons form,
  the idiom of the other functional rows. The compiler could lower it to the in-place `prepend`
  kernel.
- **With one worker thread, the stack pool hits a cliff, but this run avoids it.** A stack class
  keeps at most 64 warm free slots (`FREE_KEEP` in `crates/cheby_runtime/src/fiber/stack.rs`),
  and a batch holds up to 1,000 live fibers. With `CHEBY_THREADS=1`, most slots are released whole
  and fault in again, which makes the run several times slower. With the default eight workers
  almost every slot is reused warm. Cheby's `bench/runtime/README.md` documents this.
- **Read Cheby's row as approximate.** Its run time is the bench run minus its 11 ms size-0 run
  (start-up and eager JIT), which assumes that both cost the same inside the bench run.
  Run-to-run spread was small: the whole process took 97 ms to 100 ms over ten runs. The
  implementation's notes record that it slows down far more than Go or rust-tokio when the CPU is
  oversubscribed. Koka's row (14 ms) is not comparable. Koka's standard `std/async` has no dynamic
  spawn (`interleaved` takes a fixed list of strands and returns no handle), so its program
  carries its own single-threaded cooperative scheduler, an effect handler with a queue. The row
  measures that scheduler, not a runtime's task primitive.
- **The compiled OS-thread rows peak near 17.6 MB.** Rust, Zig, Odin, C++ and Nim run up to 1,000
  threads per batch and peak at 17.5 MB to 17.9 MB, against 11.7 MB for Go and 24.3 MB for
  Cheby. Their time is mostly kernel time: Rust's 805 ms run spent 1.77 s of CPU in the kernel.
  OCaml's systhreads peak at 81.2 MB and Ruby's threads at 151 MB.

- **Cheby has the fastest row, but at this size it ties with Go.** Its estimated run time is
  ≈ 20 ms [17 ms–23 ms], and the whole process takes 31 ms. Go takes 28 ms [19 ms–34 ms],
  including 1.8 ms of start-up, so Go is ahead on whole-process time. As the SPEC says, both rows
  are dominated by start-up and noise, so they should not be ranked against each other. The
  rust-tokio variant takes 34 ms. Every other language is far behind. Swift takes 98 ms (4.95×
  Cheby's estimate), Java 207 ms (10.5×), the BEAM rows 238 ms to 272 ms (12.0× to 13.8×), Rust
  538 ms (27.2×) and OCaml's systhreads 4.57 s (231×).
- **Capacity-0 channels let the pipeline run on several cores.** Each handoff works as in
  ping_pong: the value goes straight into the parked receiver's wait node, and the receiver takes
  the runnext slot (`crates/cheby_runtime/src/fiber_ops/channel.rs`). With 801 stages, idle
  workers steal runnable stages, so different parts of the pipeline run at the same time. The
  whole run used 140 ms of user CPU in 31 ms of wall time, and Go shows the same pattern (183 ms).
  In a scratch run at a larger `n`, `CHEBY_THREADS=1` was several times slower than the default
  eight workers. The BEAM rows follow the SPEC's pull protocol. It keeps one message in flight in
  the whole pipeline, so their stages cannot overlap.
- **The per-message costs from ping_pong apply here too, and they come from the current
  implementation.** Each receive allocates an `Ok(value)` cell, since `channel::receive` returns a
  `Result` (D-054). Each send grows a heap worklist to mark a plain integer shared (D-705,
  `crates/cheby_runtime/src/rc.rs`). In a profile at a larger `n`, the stack switch comes first,
  then the channel kernels and these allocations.
- **Shutdown is cheap because the stages are detached.** The program starts every stage with
  `fiber::spawn_detached` and returns from `main`, and the runtime kills the remaining fibers at
  exit (D-073). The tail's receiver is dropped when `primes` returns, so the last filters can end
  on their own. Nothing waits for the pipeline to drain.
- **Peak memory grows with the number of fibers.** Cheby peaks at 35.0 MB, against 21.3 MB for
  ping_pong's two fibers. Go peaks at 6.9 MB and rust-tokio at 3.8 MB. Each of the 802 fibers has
  its own stack slot (8 MiB of address space, D-125), with its control block at the top (D-677),
  and it touches at least one 16 KiB page of that slot on Apple silicon. In scratch runs, peak
  memory grew by about that much for each extra fiber. The BEAM rows peak at 74.5 MB to 76.6 MB.
- **Some rows do slightly different work.** Cheby's run time is an estimate: its bench run minus
  its 11 ms size-0 run, which includes eager JIT of the whole program. Rust-tokio, Python, Nim and
  Ruby use capacity-1 channels, so their stages can run one number ahead and do a few percent
  more filter work. Koka's 53.4 s row is not comparable: its `std/async` has no dynamic spawn, so
  each handoff costs O(pipeline depth).
- **Blocking condition variables slow the C++ row.** C++ takes 1.99 s, 3.71× Rust, and spent
  11.8 s of CPU in the kernel. Its implementation's notes trace this to libc++ on macOS, whose
  condition variable sleeps in the kernel at once. Rust's zero-capacity channel spins briefly
  before it parks.

  M = 2). Every `+`, `*`, `/` and `%` is checked, because overflow panics (D-025, language design),
  and each source location gets one cold panic path for each kind of panic. Cheby's back end emits
  the zero and overflow tests even for a literal divisor (`cheby_codegen_clif/src/arith.rs`), and
  with Cranelift's optimiser off (D-259) nothing folds them, so `a / 31` keeps both. Every function
  returns one uniform word (D-453), so each call to `base` or `step_j` is followed by a tag test and
  an inline reference-count drop of the result. Each call also goes through the JIT's indirection
  slot (D-043).
- **The module constant `modulus` costs the most avoidable work.** It has 45 uses per module. Today
  a constant's value is linked in as data, not folded into the code (D-257 sets this for debug
  builds), and the JIT fills its slot only after compiling (D-535). So each use loads the slot,
  checks that it was filled, and `dup`s, unboxes and `drop`s the value, although the initializer is
  a literal. This is the current implementation: D-257 lets release builds export small scalar
  values like this one so they can be folded. In a scratch copy at a smaller M with the constant
  replaced by the literal, the back end ran markedly faster and the machine code was markedly
  smaller. SPEC.md asks for a named constant, so idiomatic code pays this cost today.
- **The rows do not do the same work.** Cheby's number is a whole `cheby run`: start-up, unoptimised
  code generation into memory (the debug profile, D-259) and a trivial `main`. It writes no file and
  links nothing, while the slower rows are release builds that write their output and, for the AOT
  languages, optimise and link it. D-267 lets a future Cheby release build take up to 3× its debug
  build. The rows ahead of Cheby are closer kin: `tsc` checks and emits JavaScript, and Python and
  Ruby compile to bytecode in memory.
- **Several toolchains build almost serially.** At M = 200, Go, Swift and OCaml used about 1.5, 1.4
  and 1.3 cores on average (CPU time over wall time), held back by the import chain (SPEC.md). Odin
  and Zig, which build one compilation unit, used about one. C++ under `make -j` used about 7.
