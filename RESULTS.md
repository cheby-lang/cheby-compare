### Notes

- **Cheby runs in 1.04 s, 1.05× Rust.** That is `cheby run` as a whole process. The `cheby build`
  executable takes 1.06 s. The two rows are 15th and 16th of 21, next to the languages that free
  node by node. Rust (991 ms) is just ahead. C++ (1.12 s), Odin (1.26 s) and Swift (1.66 s), which
  also counts references (ARC), are behind. Most tracing collectors lead: Java 255 ms, Go 612 ms,
  OCaml 703 ms (Cheby 1.47×), Gleam 747 ms (1.39×) and Erlang 792 ms (1.31×). Koka, the closest
  model to Cheby (Perceus over mimalloc), is the one reference-counted language far ahead, at 396 ms
  (Cheby 2.62×).
- **Peak RSS is 51.7 MB under `cheby run`, against 17.9 MB for Rust and 254 MB to 413 MB for the
  BEAM and the JVM.** 16.4 MB of it is the floor of every `cheby run` process, which carries the
  compiler and the JIT: that is what `hello_world` peaks at. The executable peaks at 57.8 MB,
  although its floor is only 3.5 MB. No run here explains why it peaks above `cheby run`. Go (37.7
  MB) and OCaml (46.6 MB), which use tracing collectors, peak below both rows.
- **The work matches the SPEC: one heap object per node, freed by its count (D-005).** The runtime's
  allocation counter (`CHEBY_RT_STATS=1`) shows one allocation per node at the test size. The SPEC
  requires one allocation and one free per node in every language, so those are not a cost of
  reference counting. What reference counting adds is small here: `check` borrows its tree, so the
  walk touches no counts, and one `drop` after `check` frees the whole tree, one decrement and one
  free per node (the program's MIR). Only that part is language design.
- **The runtime's own allocation and free path takes as much time as the compiled code.** A profile
  of the executable at the bench size puts 44% of the samples in the runtime's allocation and free
  code and 44% in the compiled `make` and `check`. In the runtime, `drain`, the loop that frees a
  tree node by node, takes 25% and `cheby_rt_alloc` 18%. mimalloc's own functions take about 6%
  (D-890). The runtime's share is current implementation. Koka, for comparison, frees each node
  inline while `check` walks it (see Koka's `impl.toml`).
- **Both rows are steady.** Ten timings span 1.03 s to 1.05 s for `cheby run` and 1.05 s to 1.07 s
  for the executable. The `cheby run` row includes its start-up, which is 7.5 ms here.
- **Outside Cheby, the allocator likely explains much of the order among the malloc/free
  languages.** Zig's nodes come from `std.heap.smp_allocator` and it runs in 504 ms, while Rust (991
  ms) and C++ (1.12 s) use the macOS system `malloc` (see Zig's `impl.toml`). No run swapped the
  allocator to confirm it. Koka's 396 ms comes from its bundled mimalloc together with freeing each
  node inline as `check` walks it (Koka's `impl.toml`).

### Notes

- **Cheby runs in 27.2 s as an executable and 28.2 s under `cheby run`, about 53× Rust.** The rows
  are 18th and 19th of 21, ahead of Ruby (29.4 s) and Python (51.4 s). The languages that rebuild
  immutable records in a list every step are its peers. Cheby is now level with Gleam (26.2 s) and
  behind Elixir (23.8 s, Cheby 1.14×), Erlang (17.2 s, 1.58×) and Koka (2.78 s, 9.80×). OCaml, with
  mutable float fields, runs in 906 ms. The October JIT took 44.0 s.
- **The language rules out the in-place version.** Cheby has no mutation and no array type (D-017,
  D-039), so each step builds new `Body` records and a new list, as the SPEC expects. Koka's 2.78 s
  shows how fast immutable records can run under Perceus reuse (D-005). Its list is a cons list
  walked by direct recursion.
- **The time goes to allocation, reference counting and lists, not to float arithmetic.** A profile
  of the executable puts 42% of the samples in the runtime's allocation and counting code, 24% in
  its `List` code and 26% in compiled code. The runtime counters (`CHEBY_RT_STATS=1`) report 63
  allocations per step: 1.39 billion over 22 million steps. `List` is an RRB vector, not a linked
  list (D-039). `list::fold` calls its closure through the uniform convention for unknown callees
  (D-453) and threads a fresh tuple accumulator. Each step also pushes and prepends to lists and
  maps over one.
- **Every record update now reuses its record in place.** The counters report 770 million reuses and
  no miss. They also report 220 million list pushes and 704 million list updates in place, against
  10 copies. In October many of these reuses missed at run time. A `[first, ..rest]` step cost three
  runtime calls then. Now the compiler writes the step inline for a list that nothing else holds,
  and calls the runtime once for any other list (D-1757 to D-1760).
- **A cons list may still be faster, but that is not measured.** In an October scratch test, the
  same step over a hand-made cons type, the shape Koka and the BEAM programs use, ran several times
  faster. Nobody has repeated the test since the list changes, so the size of that gap today is
  unknown.
- **Floats are mostly not boxed here.** A record keeps its `Float` fields raw (D-562,
  `docs/plan/architecture.md`), so reading and building bodies moves no boxed floats. The exception
  is `float::sqrt`, once per pair: a native external returns through a Cheby-ABI wrapper as a
  uniform word (D-455, D-453), so its result is a boxed `Float`. Boxing takes under 3% of the
  samples.
- **The executable needs little memory.** It peaks at 3.8 MB, against 1.8 MB for Rust. `cheby run`
  peaks at 18.4 MB, and 16.4 MB of that is the floor of any `cheby run` process (`hello_world`).
  Runs over 5 s get 3 timings: 27.2 s to 27.3 s for the executable and 28.1 s to 30.3 s for `cheby
  run`.

### Notes

- **Cheby runs in 21.5 s on both rows, 27× Rust.** The rows are 18th and 19th of 21, ahead of Ruby
  (50.4 s) and Python (77.4 s, one timing). The list-walking languages are the fair comparison, and
  all are ahead: Gleam 18.1 s (Cheby 1.19×), Elixir 9.51 s (2.26×), Erlang 8.58 s (2.50×) and Koka
  5.96 s (3.60×). The October JIT took 52.6 s.
- **No arrays is language design, and it shapes the program.** Cheby has no array type (D-039), so
  the vectors are `List<Float>` walked front to back, as in the BEAM languages and Koka. A `Float`
  inside a `List` is a boxed heap object (D-521), so every element read touches a separate object
  and updates its count.
- **`float::from_int` allocates on every matrix entry.** It is a native external, and a native
  external is called through a Cheby-ABI wrapper that returns one uniform word (D-455, D-453). Its
  `Float` result is boxed, then unboxed and freed by the caller. The runtime counters
  (`CHEBY_RT_STATS=1`) report 1.21 billion allocations, one per inner step: 40 passes over 5,500²
  entries. A profile of the executable puts 41% of the samples in allocating, counting and freeing.
  In an October scratch test at a smaller `n`, carrying the indices as `Float`, with no conversion
  in the inner loop, cut the run time by more than half. That test has not been repeated. The cost
  is current implementation.
- **A `[xj, ..tail]` step is one runtime call here, down from three.** The compiler writes the step
  inline for a list whose leaf nothing else holds (D-1759). Here every row walks the same vector, so
  its leaves stay shared and each step calls `cheby_rt_list_uncons_owned`, which takes 13% of the
  samples. The first step of every row copies the root of the shared list: the counters report
  220,002 copies, one per row, against 1.21 billion steps in place. The runtime's list code takes
  18% of the samples in all, and compiled code 33%.
- **The program is already tuned around the boxing.** `A(i, j)` is written out in both inner loops
  instead of being a helper, because a `Float` returned from a function is boxed (D-453). The Cheby
  `impl.toml` records the measurement behind that choice.
- **Boxed float returns are not unique to Cheby.** OCaml marks its entry helper `[@inline]`, since
  `ocamlopt` without flambda boxes a returned float, and Erlang and Elixir ask their compilers to
  inline `a/2` (their `impl.toml` files).
- **The executable needs little memory.** It peaks at 4.7 MB, against 1.9 MB for Rust. `cheby run`
  peaks at 19.1 MB, and 16.4 MB of that is the floor of any `cheby run` process (`hello_world`).

  each step. The call overhead and the constant load are current implementation.

  allocations, 13.7 million per pass over the file. Each byte the parser reads is a call through

- **Cheby runs in 25.8 s as an executable and 26.5 s under `cheby run`, about 40× Rust.** The rows
  are 17th and 18th of 21, against 660 ms for Rust. Cheby sits among the other rows that keep two
  persistent maps. Gleam (24.5 s) is just ahead, and Clojure (27.9 s), Elixir (31.6 s) and Erlang
  (31.7 s) are behind. Koka (14.0 s) is 1.84× faster and OCaml (2.52 s) 10.2×. The executable's peak
  RSS is 18.2 MB, and `cheby run`'s is 33.4 MB: well under Erlang and Elixir (about 320 MB), Gleam
  (247 MB) and Clojure (2.1 GB), but over Rust's 11.3 MB. The October JIT took 31.3 s.
- **Without mutation there is no linked list, by design.** Cheby has no mutable state (D-017), so
  neither shape B's doubly linked list nor an in-place `LinkedHashMap` can be written. Its shape A,
  `std::ordered_map`, is shape C inside: a `Map<K, (Int, V)>` plus a `SortedMap<Int, K>` from
  insertion number to key (`std/ordered_map.cheby`, D-336). So the rows to compare with are the
  other shape C rows (Erlang, Elixir, Clojure, Gleam, Koka), and Cheby lands among them.
- **A hit costs four hash operations and two tree updates.** `ordered_map` has no move-to-end, so a
  hit is `get`, `remove` and `insert` (D-340). `get` is a hash lookup. `remove` starts with its own
  lookup, then removes from the hash trie and from the tree. `insert` is one `map::upsert` and a
  tree insert. A miss in a full cache also pays for `first`, which reads the tree and looks the key
  up, and for the `remove` that evicts. Every `map::get` that finds its key also allocates a `Some`.
  A move-to-end or pop-first operation in the standard library would save part of this work.
- **Most of the time is the sorted tree, in compiled Cheby code.** A profile of the executable puts
  73% of the samples in compiled code, most of it `std::sorted_map`: `sorted_map::balanced` alone
  takes 19%. The runtime's hash-trie kernels take 19%, and allocation and reference counting 7%.
  Without mutation, an O(log n) weight-balanced tree (`std/sorted_map.cheby`) stands where shape B
  has an O(1) linked list. That tree compares keys through the `Compare` dictionary (D-046), because
  generic code is not yet specialized (D-021): `int::compare` and the shim that calls it take 12% of
  the samples. Specialization is planned for M6 (D-251). Persistence alone does not explain the gap:
  Koka's persistent tree is 1.84× faster here.
- **The cache is updated in place.** Only the loop holds the cache, so Perceus reuse writes rebuilt
  tree nodes over the old ones and the hash trie changes in place. The runtime counters
  (`CHEBY_RT_STATS=1`) report 809 million reuses against 8.6 million misses, and 39.9 million map
  updates in place, two per operation, with none copied.
- **The rows use three shapes.** Java, Scala, Ruby, Python and Cheby use an ordered map (A). Rust,
  C++, Go, C#, TypeScript, Swift, Zig, Odin, Nim and OCaml use a hash map plus a linked list (B).
  The BEAM languages, Clojure and Koka use two persistent maps (C), and Koka writes its own tree.
  Runs over 5 s get 3 timings: 25.6 s to 28.1 s for Cheby's executable and 25.5 s to 26.5 s for
  `cheby run`.
- **Ruby beats two shape B rows with a plain `Hash`.** Its delete-and-reinsert hit (2.06 s) is
  faster than OCaml (2.52 s) and TypeScript (2.65 s), which both keep a hash map plus a linked list.

  `Ok(value)` cell for every value received (`values::ok` in `channel.rs`). `CHEBY_RT_STATS=1`

  expects that "a message allocates nothing", but that does not hold today. The language does not
  require the allocation. A send allocates nothing now: `channel::send` marks the value shared
  (D-705), and `rc::mark_shared` returns at once for a plain integer, where in October it grew a
  worklist first.
- **The stack switch is the largest cost left.** Cheby's own `fiber/ping_pong` benchmark, which runs
  long enough to profile, spends most of its time in the return after the stack switch

### Notes

- **Cheby's executable is seventh of the 23 comparable rows, at 76 ms.** Its ten timings span 75 ms
  to 76 ms, and `cheby run` takes 84 ms as a whole process. Go (16 ms, 4.62× faster), Swift (59 ms),
  TypeScript (62 ms) and C# (72 ms) are ahead. So are the rust-tokio (29 ms) and OCaml Eio (62 ms)
  variants. Java's virtual threads come right behind at 96 ms. Erlang takes 157 ms (2.07× the
  executable), Gleam 197 ms and Elixir 342 ms. Rust's OS threads take 805 ms, 10.6× the executable.
- **Each task does only ten generator steps, so the rows measure spawn and join.** A Cheby spawn
  allocates the closure and a `Fiber` handle with its join cell, and marks the closure shared
  (D-705). It also takes a stack slot (8 MiB of address space, D-125, with free slots reused warm,
  D-677), builds a control block, and records the fiber in its scope under the scope's lock
  (`crates/cheby_runtime/src/fiber_ops/scope.rs`). The new fiber takes the runnext slot. The fiber
  it displaces goes to the worker's deque, and an idle worker is woken through a condition variable
  (`schedule` and `notify_parked` in `crates/cheby_runtime/src/sched/mod.rs`). Each fiber takes the
  scope's lock again when it ends. The locking, the condition-variable wake-ups and the separate
  handle and join-cell allocations are the current implementation. Registering each fiber with its
  scope (structured concurrency, D-040) and giving each fiber its own stack (D-125) are design
  choices.
- **The program's `[fiber, ..fibers]` costs a third of the run, which is the current
  implementation.** `List` is an RRB-tree vector, not a linked list (D-039, language design). The
  compiler lowers `[x, ..xs]` to a push onto a new list and an append of `xs`, which allocates new
  tree nodes for every task. `CHEBY_RT_STATS=1` counts 7.9 allocations per task. A scratch copy that
  used `[..fibers, x]`, which updates the list in place, made 3.0 per task and ran in 51 ms against
  77 ms. The program keeps the cons form, the idiom of the other functional rows. The compiler could
  lower it to the runtime's in-place prepend. Cheby's `docs/perf/optimization-log.md` lists that
  change as a proposal that needs a decision.
- **The run spends 37 ms in the kernel, against 9 ms for Go.** In October's profile at a larger `n`,
  the spawn path was the largest item, followed by the slow path of the scope's lock, where the
  spawner and the ending fibers meet, and by condition-variable waits and signals. This run is too
  short to profile, and that profile has not been repeated.
- **With one worker thread, the stack pool hits a cliff, but this run avoids it.** A stack class
  keeps at most 64 warm free slots (`FREE_KEEP` in `crates/cheby_runtime/src/fiber/stack.rs`), and a
  batch holds up to 1,000 live fibers. With `CHEBY_THREADS=1`, most slots are released whole and
  fault in again: the same executable took 608 ms, 495 ms of it in the kernel. With the default
  eight workers almost every slot is reused warm. Cheby's `bench/runtime/README.md` documents this.
- **Koka's row is not comparable.** Koka's standard `std/async` has no dynamic spawn (`interleaved`
  takes a fixed list of strands and returns no handle), so its program carries its own
  single-threaded cooperative scheduler, an effect handler with a queue. The row (14 ms) measures
  that scheduler, not a runtime's task primitive. The Cheby implementation's notes record that it
  slows down far more than Go or rust-tokio when the CPU is oversubscribed.
- **The compiled OS-thread rows peak near 17.6 MB.** Rust, Zig, Odin, C++ and Nim run up to 1,000
  threads per batch and peak at 17.5 MB to 17.9 MB, against 11.7 MB for Go, 7.3 MB for Cheby's
  executable and 22.6 MB for `cheby run`. Their time is mostly kernel time: Rust's 805 ms run spent
  1.77 s of CPU in the kernel. OCaml's systhreads peak at 81.2 MB and Ruby's threads at 151 MB.

- **Cheby has the two fastest rows, but at this size the executable ties with Go.** The executable
  takes 19 ms [19 ms–21 ms] and `cheby run` 26 ms [25 ms–31 ms] as a whole process. Go takes 28 ms
  [19 ms–34 ms]. As the SPEC says, these rows are dominated by start-up and noise, so they should

  behind. Swift takes 98 ms (5.05× the executable), Java 207 ms (10.7×), the BEAM rows 238 ms to 272
  ms (12.3× to 14.0×), Rust 538 ms (27.8×) and OCaml's systhreads 4.57 s (235×).
- **Capacity-0 channels let the pipeline run on several cores.** Each handoff works as in
  `ping_pong`: the value goes straight into the parked receiver's wait node, and the receiver takes
  the runnext slot (`crates/cheby_runtime/src/fiber_ops/channel.rs`). With 801 stages, idle workers
  steal runnable stages, so different parts of the pipeline run at the same time. The executable
  used 104 ms of user CPU in 19 ms of wall time, and Go shows the same pattern (183 ms). With
  `CHEBY_THREADS=1` the same executable took 57 ms, three times as long. At `n = 3000` it took 845
  ms against 177 ms. The BEAM rows follow the SPEC's pull protocol. It keeps one message in flight
  in the whole pipeline, so their stages cannot overlap.
- **The per-message cost from `ping_pong` applies here too, and it comes from the current
  implementation.** Each receive allocates an `Ok(value)` cell, since `channel::receive` returns a
  `Result` (D-054). A send of a plain integer allocates nothing (D-705,
  `crates/cheby_runtime/src/rc.rs`). The run makes 467,294 allocations. Cheby's own `fiber/sieve`
  benchmark, which runs long enough to profile, spends 40% of its samples in the stack switch
  (`docs/perf/optimization-log.md` in the Cheby repository).
- **Shutdown is cheap because the stages are detached.** The program starts every stage with
  `fiber::spawn_detached` and returns from `main`, and the runtime kills the remaining fibers at
  exit (D-073). The tail's receiver is dropped when `primes` returns, so the last filters can end on
  their own. Nothing waits for the pipeline to drain.
- **Peak memory grows with the number of fibers.** The executable peaks at 18.1 MB, against 3.9 MB
  for `ping_pong`'s two fibers. That is about 18 KiB for each of the 800 extra fibers. Each fiber
  has its own stack slot (8 MiB of address space, D-125), with its control block at the top (D-677),
  and it touches at least one 16 KiB page of that slot on Apple silicon. `cheby run` peaks at 33.3
  MB. Go peaks at 6.9 MB and rust-tokio at 3.8 MB. The BEAM rows peak at 74.5 MB to 76.6 MB.
- **Some rows do slightly different work.** Rust-tokio, Python, Nim and Ruby use capacity-1
  channels, so their stages can run one number ahead and do a few percent more filter work. Koka's
  53.4 s row is not comparable: its `std/async` has no dynamic spawn, so each handoff costs
  O(pipeline depth).
- **Blocking condition variables slow the C++ row.** C++ takes 1.99 s, 3.71× Rust, and spent 11.8 s
  of CPU in the kernel. Its implementation's notes trace this to libc++ on macOS, whose condition
  variable sleeps in the kernel at once. Rust's zero-capacity channel spins briefly before it parks.

### Notes

- **A cold `cheby run` of the 200-module project takes 571 ms, 4th of the 20 ranked rows, and `cheby
  build` takes 716 ms, 5th.** Only Ruby (89 ms), TypeScript's `tsc` (99 ms) and Python (234 ms) are
  faster, and none of them compiles the project to machine code. Erlang takes 739 ms and Gleam 818
  ms. Rust's clean release build takes 1.64 s, 2.29× the Cheby build. Go takes 2.99 s (4.18×) and
  OCaml 13.7 s (19.1×). At M = 1 `cheby run` takes 19 ms, level with Python (20 ms) and ahead of
  every other row. Koka is not ranked, because its build fails at M = 200.
- **Both rows now fill the build cache, which the October JIT did not have.** In October `cheby run`
  compiled the project into memory in 242 ms and kept nothing. Now a cold run also stores each
  module's compiled code: in a scratch run the cache grew from 4 MB to 42 MB. The second run of the
  same project took 106 ms.
- **The module constant costs half of the cold time.** Every module declares `priv const modulus:
  Int = 1000003` and uses it 45 times. Each constant is evaluated on code compiled in a JIT module
  of its own, and stored as a cache entry of its own (D-977 to D-979). Module code reads a constant
  only through its slot, so each use loads the slot, checks that it is filled, and dups and drops
  the value. In a scratch copy with the constant replaced by the literal, a cold `cheby run` took
  262 ms against 538 ms, a cold `cheby check` 59 ms against 302 ms, and a cold `cheby build` 346 ms
  against 757 ms. The executable shrank from 11.5 MB to 9.4 MB. D-257 lets release builds fold small
  scalar constants like this one. SPEC.md asks for a named constant, so idiomatic code pays this
  cost today.
- **On CPU time, Cheby is level with Erlang and Gleam.** The cold run used 3.01 s of CPU time (user
  plus system), about five cores busy for 571 ms. Ruby used 87 ms and Python 234 ms, each on one
  core, and `tsc` 448 ms. Erlang used 3.66 s, Gleam 3.70 s and Rust 5.83 s. Per module (the slope
  from M = 1 to M = 200, from the JSON) `cheby run` adds 2.8 ms of wall time and 15 ms of CPU time,
  and `cheby build` 3.3 ms and 16 ms. Ruby adds 0.31 ms and Python 1.1 ms of both. `tsc` adds 0.32
  ms of wall and 1.6 ms of CPU time, Erlang 2.6 ms and 16 ms, and Rust 7.7 ms and 29 ms.
- **The front end is half of the cold run.** A cold `cheby check` of the project takes 304 ms and 15
  ms at M = 1, a slope of 1.5 ms per module. Most of it is the 200 constants: the scratch copy
  without them checked in 59 ms. On a warm cache `cheby check` took 86 ms.
- **One thread is not the budget's measurement.** A cold `cheby run -j 1` took 1.92 s for the
  project's 33,008 lines, about 17k lines per second. Cheby's own budget is 100k lines per second
  per core for checking plus code generation (D-247). This row is a whole process: it also starts
  up, evaluates 200 constants, writes the cache and runs `main`.
- **The rows do not do the same work.** `cheby run`'s number is a whole process: start-up,
  unoptimised code generation (the debug profile, D-259), cache writes and a trivial `main`. `cheby
  build` also links an executable, still unoptimised. The slower rows are release builds that
  optimise their output. D-267 lets a future Cheby release build take up to 3× its debug build. The
  rows ahead of Cheby are closer kin to `cheby run`: `tsc` checks and emits JavaScript, and Python
  and Ruby compile to bytecode in memory.
- **Several toolchains build almost serially.** At M = 200, Go, Swift and OCaml used about 1.5, 1.4
  and 1.3 cores on average (CPU time over wall time), held back by the import chain (SPEC.md). Odin
  and Zig, which build one compilation unit, used about one. C++ under `make -j` used about 7.
